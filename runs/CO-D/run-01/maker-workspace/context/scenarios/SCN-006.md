Scenario ID: SCN-006
Title: Label a link, reusing existing labels instead of breeding duplicates
Type: Happy Path
Approval status: approved
Approval session: SESSION-001
Approval cycle: 1

## Approved behaviour
A link can carry several labels at once (e.g. a recipe is both "cooking" and
"italian") — no single-folder prison. Opening a link's label editor shows the
labels already on it as removable chips, and offers a combined adder ("Both"
style): the client's existing labels sit there as tappable chips AND a text box
filters them as the client types, offering to create a new label only when none
fit.

The adder actively steers reuse: it treats labels case-insensitively, so typing
"Cooking" reuses the existing "cooking" rather than creating a near-duplicate.
Labels are removed by clicking the × on a chip.

## Gherkin
Feature: Label a link

  Scenario: A link can hold multiple labels

    When the client adds "cooking" and "italian"

  Scenario: Reuse an existing label regardless of letter case
    Given the client already has a label "cooking"
    When the client types "Cooking" while adding a label
    Then the app reuses the existing "cooking" and does not create a duplicate

  Scenario: Existing labels are offered for reuse
    Given the client has existing labels
    When the client opens the label adder
    Then the existing labels are shown to tap
    And typing filters them; a new label is created only when none match

  Scenario: Remove a label
    Given a link has a label
    When the client clicks the × on that label chip
    Then the label is removed from the link

## Assumptions
- "Both" adder style is the approved default (tap-to-reuse + type-to-filter).
- Case-insensitive matching prevents "cooking"/"Cooking" duplicates; a brand-new
  label is stored as typed.
- A brand-new label becomes available across the app (appears in the Labels bar).
- Undo of an accidental removal is a parked future nicety (see goals parking lot).
