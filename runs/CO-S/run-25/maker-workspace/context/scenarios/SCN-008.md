Title: Manage links — edit fields, prevent duplicates, delete permanently
Type: Happy Path
Approval status: approved

Approval cycle: 1

## Approved behaviour

### Edit
The client can edit a saved link's title, address, and description in one form.
- If only the title and/or description are changed (address unchanged), the
  client's entered values are kept exactly.
- If the address is changed, the app treats it as a new page: it re-fetches the
  new page's title and description and captures a fresh saved copy dated now, while
  keeping the client's tags and note attached. (Keeping the old page's copy under a
  new address would be misleading.)

### Duplicate prevention
When the client saves an address that already exists in the library (or archive),
no duplicate is created. Instead a notice states it is already saved and offers to
show the existing link (switching to the right view and highlighting it). Two
addresses are treated as the same when they differ only by http/https, a leading
"www.", a trailing slash, or a "#section" marker; a different query string counts
as a potentially different page. The same duplicate check applies when editing an
address to one already used by another link (the edit is blocked with a message).

### Delete
The client can delete a link. Because deletion is permanent and irreversible, a
confirmation is shown that states the link and its saved copy, tags, and notes will
be permanently removed. On confirmation the link is removed; on cancel nothing
changes. There is no separate trash; a confirmation is the safeguard. (Delete is
distinct from Archive, which hides recoverably.)

## Gherkin
Feature: Manage saved links

  Scenario: Edit title/description only
    Given a saved link
    When the client edits the title and/or description without changing the address
    Then the entered title and description are saved exactly

  Scenario: Edit the address
    Given a saved link with tags and a note
    When the client changes the address to a different page
    Then the link keeps its tags and note
    And the app re-fetches the new page's title and description
    And a fresh saved copy is captured, dated now

  Scenario: Prevent duplicate on save
    Given an address already exists in the library or archive
    When the client saves that address (ignoring http/https, www., trailing slash, #fragment)
    Then no duplicate is created
    And a notice offers to show the existing link

  Scenario: Different query string is not a duplicate
    Given a saved address
    When the client saves the same path with a different query string
    Then it may be saved as a separate link

  Scenario: Edit address collision
    Given two saved links
    When the client edits one link's address to match the other's
    Then the change is blocked with a message

  Scenario: Delete with confirmation
    Given a saved link
    When the client chooses Delete
    Then a confirmation warns the removal is permanent
    And confirming removes the link and its saved copy, tags, and notes
    And cancelling leaves the link unchanged

## Assumptions
- Duplicate equivalence: scheme, leading www., trailing slash, and #fragment are
  ignored; query string is significant.
- No trash/recycle bin; permanent delete guarded by confirmation.
- Address change re-derives page details and saved copy but preserves user-authored
  tags and note.
