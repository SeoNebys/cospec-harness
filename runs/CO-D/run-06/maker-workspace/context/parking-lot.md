# Parking lot — functional ideas raised but not yet explored

These are candidate scenarios the client surfaced but explicitly deferred. Keep so
they are not lost; explore in a later loop / cycle when the client is ready.

| # | Idea | Raised | Client's framing | Status |
|---|------|--------|------------------|--------|
| P1 | A "to-read / haven't gotten to it yet" status, distinct from "set aside". | SESSION-001 / C1 | "There's 'done, tuck it away' and there's 'haven't gotten to it yet, remind me' — those feel different to me." Connects to original pain: tabs "left open forever hoping I'll get to them". | DONE — approved as SCN-011 |
| P2 | Flexible combining beyond AND: OR ("any of these") and NOT ("not X"). | SESSION-001 / C1 | "A way to say 'either of these' or 'this but not that' when I need it." | DONE — approved as SCN-010 |
| P3 | **Keep the app's own saved copy (snapshot) of each page as it was at save time**, so the content survives even if the original site dies. | SESSION-001 / C1 | **HIGH PRIORITY / strongly wanted — client's explicit words: "the truest answer to why I'm building this at all… put it on the record as something I really want, not a throwaway. Don't let it quietly disappear."** With personal notes, a dead bookmark keeps all its value. Client will NOT insist it blocks v1 *if* it's genuinely a lot of work — decide scope deliberately, do not drop it. | deferred from v1 by client (pending effort assessment) — REVISIT explicitly |
| P5 | **Backfill copies when the server goes live.** When real capture is deployed, retroactively make copies of bookmarks already saved (those marked "no copy" because capture wasn't available yet) — not only new saves. | SESSION-001 / C3 | Client's explicit worry: "if it's only new ones, my whole existing collection stays unprotected and I might not realize it… I'd think 'keep a copy' is on, but my older, more important saves would still have nothing behind them." Wants automatic backfill, or at least an easy "grab copies for these" nudge for the "no copy" ones. Design groundwork: capture.js already distinguishes reason 'unreachable-in-client' (retry-able) from 'gated' (genuinely can't). HIGH — pairs with standing up the server piece. | ON ROADMAP (tie to server deployment) |
| P4 | Dead-link handling, behaviour (c): no background checking; but when the client clicks a link and it's plainly gone, offer help ("this didn't load — set it aside, or find another copy?"), including pointing to an archived version of the page on the web. | SESSION-001 / C1 | Client rejected (b) proactive background checks ("crying wolf trains me to ignore warnings") and (a) do-nothing. Wants help only at the moment of a real failure. Ties to P3 (own copy is the first "copy" offered). | "nice someday" — explicitly NOT for v1; don't slow first build |
