Scenario ID: SCN-004
Title: Re-saving a link already saved does not create a duplicate
Type: Edge Case
Approval status: approved
Approval session: SESSION-001
Approval cycle: 1

## Approved behaviour
When the client saves a link that is already in their list, the app does not
create a second copy. Instead it takes the client to the existing saved link,
briefly highlights it, shows a short "you already saved this one" note, and opens
that link ready to edit (in-place rename) so the client can tweak it. There is no
confirmation popup — the client explicitly rejected being asked every time.

Two links are considered the same page when the site host and the path match,
ignoring a leading "www." and a trailing "/".

## Gherkin
Feature: Duplicate save handling

  Scenario: Saving a link that already exists
    Given the client already has a saved link for a page
    When the client saves the same page again
    Then no second copy is created
    And the app scrolls to and highlights the existing link
    And the app opens that link ready to edit
    And a brief "you already saved this one" note is shown

  Scenario: Same page with www or trailing slash differences
    Given the client has saved "https://example.com/article"
    When the client saves "https://www.example.com/article/"
    Then it is treated as the same page and no copy is created

  Scenario: No confirmation prompt on duplicate
    Given the client saves a page they already have
    When the duplicate is detected
    Then the client is not asked a yes/no question
    And the app proceeds straight to the existing link

## Assumptions
- Duplicate matching normalizes leading "www." and trailing "/".
- Tracking-parameter normalization (e.g. "?utm_*") is NOT yet handled; it is
  parked as a required follow-up (see goals parking lot) — until then, links
  differing only by tracking junk may still slip through as separate.
- "Ready to edit" currently means the in-place quick rename (SCN-003); it will
  extend when the full edit view exists.
