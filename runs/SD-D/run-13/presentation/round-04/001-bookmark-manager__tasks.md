## Dependencies and Execution Order

### Phase dependencies

- **Phase 1 — Setup**: Starts immediately. T002–T004 and T006 may proceed in parallel after the package shape in T001 is known; T005 completes the scaffold.
- **Phase 2 — Foundational**: Depends on Phase 1 and blocks all stories. T007–T009 may proceed in parallel; T010 precedes migrations T011–T014; T015 depends on the migrated schema; server/client/test composition T016–T021 can then converge.
- **Phase 3 — US1**: Depends on Foundation. This is the suggested MVP.
- **Phase 4 — US2**: Depends on Foundation. Parser, evaluator, repository, and component work can run against seeded records in parallel with US1, but T054 integrates with the US1 form/list before the story checkpoint.
- **Phase 5 — US3**: Depends on Foundation and the collection-query contract from US2 for its complete scoped view; backend state work may begin earlier.
- **Phase 6 — US4**: Depends on Foundation and the US1 create/detail flow; it reuses the US2 tag component when present, but note/schema work is independently parallelizable.
- **Phase 7 — US5**: Depends on Foundation, active bookmark behavior from US1, shared collection querying from US2, and preserved read state from US3.
- **Phase 8 — Polish**: Depends on all stories selected for release; T082–T085, T087–T088, and T091 can proceed in parallel before final browser/runtime/usability validation T086, T089–T090, and T092.

### User-story dependency graph

```text
Setup → Foundation → US1 (MVP) ─────────────┬→ US4
                  └→ US2 → US3 ─────────────┼→ US5
                          └───────────────────┘
US1 + US2 + US3 + US4 + US5 → Polish/Release Validation
```

- **US1** supplies capture, persistence, detail, and strict duplicate behavior.
- **US2** can develop its search engine/API against seeded foundational data, then integrate with US1's collection UI.
- **US3** reuses US2's view-scoped query controls but owns read-status transitions.
- **US4** extends US1's create/detail domain and reuses US2's tag entry.
- **US5** consumes prior preserved states so archive/restore can prove they survive.

### Within each user story

1. Write the listed tests and verify they fail for the intended missing behavior.
2. Implement pure schemas/domain logic.
3. Implement repositories/services and transaction boundaries.
4. Implement API routes and validate contract shapes.
5. Implement UI components and route integration.
6. Run the story's unit, integration, contract, component, and browser tests until the independent checkpoint passes.

## Implementation Strategy

### MVP first

1. Complete Setup (T001–T006).
2. Complete Foundation (T007–T021).
3. Complete US1 tests then implementation (T022–T040).
4. Stop and validate the US1 checkpoint: paste, retrieve, override, save, persist, view/open, and redirect duplicates.
5. Present the runnable MVP before adding organization features if an intermediate review is desired.

### Incremental delivery

1. **US1**: Reliable low-effort capture and duplicate safety.
2. **US2**: Scalable finding, tags, favorites filtering, and sorting.
3. **US3**: Actionable read-later workflow.
4. **US4**: Complete maintenance and formatted context.
5. **US5**: Reversible cleanup and confirmed permanent deletion.
6. **Polish**: Whole-product security, accessibility, performance, and runtime proof.

### Completion discipline

- Do not mark a task complete until its named files and assertions exist and the relevant command passes.
- Preserve test-first order within each user story.
- Stop at every story checkpoint to ensure the increment works independently.
- If implementation reveals different required product behavior, return to `spec.md` and the approval gate instead of silently changing scope.
