# Implementation Plan: Personal Bookmark Manager

**Branch**: `001-manage-bookmarks` | **Date**: 2026-09-26 | **Spec**: [spec.md](spec.md)

**Input**: Approved feature specification from `specs/001-manage-bookmarks/spec.md`

## Summary

Build a responsive personal bookmark manager as one TypeScript application. A React single-page interface provides the Library and Read Later views; an Express server exposes a same-origin JSON API, serves the production UI, persists bookmarks and normalized tags in a local SQLite database, and retrieves page titles and descriptions through a tightly constrained server-side metadata service. The single-process design meets the one-user, one-installation scope without introducing accounts, external services, or independently deployed components.

## Technical Context

**Language/Version**: TypeScript 5.9 on Node.js 24 LTS; modern browser JavaScript generated by Vite

**Primary Dependencies**: React 19.3, React DOM 19.3, Vite 8.3, Express 5.2, Zod 4.6, `better-sqlite3` 13, Undici 8.11, Cheerio 1.2, `ip-address` 10.7, Helmet 8.3

**Storage**: One local SQLite file at `data/bookmarks.sqlite`, accessed through `better-sqlite3`; versioned SQL migrations and foreign-key enforcement

**Testing**: Vitest 5 for shared/server unit tests, jsdom with React Testing Library for components, Supertest for HTTP integration, and Chromium through `@playwright/test` pinned to 1.61.0 for end-to-end validation

**Target Platform**: Current evergreen desktop and mobile browsers; Node.js 24 LTS server on Linux for the review/runtime environment

**Project Type**: Single-package web application with browser client and same-origin server

**Performance Goals**: Search/filter/sort updates visible within 1 second at 1,000 bookmarks; page metadata returned or failed safely within a 4-second service budget so the UI resolves within 5 seconds; ordinary CRUD feedback perceived as immediate

**Constraints**: Listen on `0.0.0.0:4000`; one foreground production command; no authentication or cross-device sync; metadata retrieval must not reach non-public network destinations; no fetched scripts or subresources; keyboard-operable responsive UI; durable state across restarts

**Scale/Scope**: One user and installation, up to 1,000 bookmarks, two top-level views, three reading states, and three relational tables plus migration metadata

## Architecture and Request Flow

```text
Browser
  └─ React SPA
      ├─ Library / Read Later UI state in URL query parameters
      └─ same-origin fetch to /api/*
            │
Express process on 0.0.0.0:4000
  ├─ Zod validation and predictable error envelope
  ├─ bookmark service ── transactions ── SQLite file
  ├─ metadata service ── guarded outbound HTTP(S) ── public page
  └─ production static files and SPA fallback
```

- Development runs the Vite client and Express API concurrently, with Vite proxying `/api` to the server.
- Production builds the client and server, then one Express process serves both from port 4000.
- Client and server share request/response types, validation schemas, URL normalization, tag normalization, and reading-state values.
- Library context, query, selected tags, and sort are represented in URL query parameters so browser history and post-mutation refreshes retain the active view without a routing or global-state library.
- The server is the source of truth for filtering, tag intersection, sorting, duplicate detection, and mutations. The client replaces only successfully refreshed data and retains the last valid list when a refresh fails.

## Metadata Retrieval Design

The metadata endpoint is a narrow preview service, never a general-purpose proxy.

1. Parse the submitted address with the WHATWG URL parser. Require an absolute `http:` or `https:` address, no embedded credentials, an effective port of 80 or 443 for retrieval, and a maximum input length of 4,096 characters. A bookmark on another HTTP(S) port may still be saved manually, but automatic retrieval reports an unavailable result.
2. Resolve every hostname using the operating system's normal lookup semantics. Reject the request if any answer is non-public, including loopback, private, link-local, carrier-grade NAT, unique-local, multicast, unspecified, documentation, benchmark, reserved, and IPv4-mapped equivalents. Reject localhost-style names and unsafe IP literals.
3. Pin the outbound connection to a validated resolved address while retaining the original hostname for the HTTP Host header and TLS verification. This removes the validation-to-connection DNS-rebinding gap.
4. Follow redirects manually, with at most three hops. Resolve relative locations and repeat the full scheme, credential, port, DNS, IP, and connection-pinning policy for every hop. Never forward cookies, authorization, proxy authorization, or referrer headers.
5. Apply one four-second wall-clock deadline across DNS, redirects, headers, and body. Allow at most four concurrent retrievals, accept only successful HTML/XHTML responses, keep bounded response headers, and stop after 512 KiB of decompressed body data or after enough head content has been collected.
6. Parse bytes without executing scripts, styles, or subresource requests. Prefer the document `<title>`, then Open Graph and Twitter title fallbacks; prefer the standard description meta element, then Open Graph and Twitter description fallbacks. Decode entities, collapse whitespace, remove control characters, and cap returned values to 300 Unicode code points for title and 1,000 for description.
7. Return only normalized text plus the requested and final URLs and a `complete`, `partial`, or `unavailable` outcome. The originally entered URL remains the bookmark destination unless the user changes it.
8. In the form, each URL change creates a new request generation and aborts the previous request. Title and description track whether their value is empty, automatic, or user-authored plus an edit version. A result is applied only when the request generation and URL still match and the field remains empty and untouched, so a late response can never overwrite a user's work.

Saving is independent of metadata success: any valid HTTP(S) address and non-empty title can be saved through the manual fallback.

## Persistence and Query Design

- Create `STRICT` SQLite tables for bookmarks, tags, bookmark/tag associations, and applied migration versions; enable foreign keys on every connection.
- Perform bookmark creation/update and tag association changes in one transaction. Delete unused tags after association changes.
- Preserve a display spelling for each tag while using a trimmed, Unicode-normalized, lowercased key for case-insensitive uniqueness and filtering.
- Store both the user's URL and a normalized duplicate-detection key. The key uses URL parsing, normalized scheme/host/default port, and removes the fragment while retaining path and query. It is indexed but deliberately not unique because acknowledged duplicates are valid.
- Use prepared statements for all values. Search uses escaped, case-insensitive matching across title, URL, description, and tags; multiple selected tags use AND semantics; every sort adds a stable ID tie-breaker.
- Full-text search is deferred because the specified 1,000-record scale can meet the one-second goal with indexed candidate selection and ordinary matching. It is reconsidered only if benchmark evidence shows a failure.
- The database location is configurable for isolated tests. Production defaults to `data/bookmarks.sqlite`; migrations run before the server accepts traffic.

## API and UI Decisions

- The versioned HTTP contract is [contracts/openapi.yaml](contracts/openapi.yaml). Routes cover health, bookmark listing/CRUD, reading-state changes, current tags, and page metadata previews.
- Create and update requests perform authoritative duplicate checks. A conflict returns the existing bookmark summary; choosing “Save anyway” repeats the request with an explicit override.
- Error responses share one code/message/field-error shape. Metadata policy or upstream failures are represented as non-blocking unavailable outcomes; malformed API requests use appropriate client-error statuses.
- Use native semantic elements, labelled controls, visible focus treatment, and polite live regions for metadata and mutation feedback. The Library and Read Later selectors follow the accessible tabs pattern.
- Edit/create uses a labelled form. Delete confirmation is inline with explicit Cancel and Delete actions, keeping focus management simple and ensuring the least destructive choice is first.
- Destination links open in a new tab with isolation attributes so the library remains available.
- The main shell receives `data-harness-ready="true"` only after the first library request succeeds or resolves to a valid empty state; loading and fatal error placeholders are not marked ready.

## Verification Strategy

- **Static gates**: formatting/linting, strict TypeScript checking, and a production build.
- **Unit tests**: URL and tag normalization; validation limits; all search/filter/sort semantics; reading-state transitions; metadata precedence and sanitization; public/non-public IPv4 and IPv6 classification; redirect/deadline/body limits; and form request-generation/edit-version behavior.
- **Integration tests**: migrations and reopen persistence in a temporary database; transactional CRUD/tag behavior; duplicate conflict and override; Read Later membership; tag cleanup; API errors; and metadata retrieval through injected DNS/HTTP fixtures covering unsafe destinations, redirects, timeouts, partial metadata, content types, and oversized bodies.
- **Component tests**: automatic fill and manual fallback, stale-response protection, duplicate choice, empty/no-result/read-later-empty states, delete cancel/confirm, live feedback, keyboard actions, and retaining existing data after refresh errors.
- **End-to-end tests**: each approved user story, reload and process-restart persistence, keyboard-only core flow, desktop/mobile widths, ARIA snapshots and focused accessibility assertions, and the 1,000-record search/filter/sort performance criterion. Browser tests use Playwright 1.61.0 and the shared installed Chromium revision; normal automated tests do not depend on the public internet.
- **Security-focused metadata cases**: IPv4 alternate forms, IPv6 and IPv4-mapped IPv6, mixed public/private DNS answers, DNS rebinding, redirects to blocked ranges, credentialed URLs, custom ports, slow or never-ending responses, decompression expansion, malformed HTML, conflicting metadata, and markup-looking text that must remain escaped.

Runnable validation steps and expected outcomes are in [quickstart.md](quickstart.md).
