Scenario ID: SCN-008
Title: Save a link whose page can't be read, and retry later
Type: Error Case
Approval status: approved
Approval session: SESSION-001
Approval cycle: 1

## Approved behaviour
When the app cannot read a page (unavailable, private, or blocked), it tells the
user and still lets them save the bookmark: the user types the title/description
themselves, a placeholder image is used, and the address is kept. The saved card
clearly states the page couldn't be read and that the page was NOT preserved (the
image is only a placeholder) — nothing implies a real saved copy exists. The card
offers "Retry now" to re-attempt collecting the page details. On a successful
retry, the icon and preview are updated and only still-blank fields (title,
description) are filled; anything the user entered is preserved. If it still can't
be read, the user is told to try later. (Re-attempting the preserved page copy
belongs to the later preservation feature.)

## Gherkin
Feature: Unreadable page handling

  Scenario: Save anyway when the page can't be read
    Given the app cannot read the page at an address
    When the user saves it
    Then the user can enter the title and description
    And a placeholder image is used and the address is kept
    And the bookmark is marked as "page not read / not preserved"

  Scenario: Retry collecting details later
    Given a saved bookmark whose page could not be read
    When the user chooses "Retry now" and the page is now accessible
    Then the icon and preview are updated
    And only still-blank fields are filled, preserving user-entered values
    And the "not read / not preserved" marker is removed

  Scenario: Retry still fails
    Given a saved bookmark whose page could not be read
    When the user retries and the page is still unreadable
    Then the user is told it still couldn't be read and to try later

## Assumptions
- Icon/preview for an unreadable page are placeholders, not a saved copy.
- Preserving the actual page copy is a later-cycle feature (L-01).
