## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel because it touches different files and does not depend on an incomplete task in the same phase.
- **[Story]**: Maps the task to an approved user story.
- Every task names the exact file or directory it changes.

## Dependencies & Execution Order

### Phase Dependencies

- **Phase 1 — Setup**: No dependencies; starts immediately.
- **Phase 2 — Foundational**: Depends on Phase 1 and blocks all user stories.
- **Phase 3 — US1**: Depends on Phase 2; delivers the MVP.
- **Phase 4 — US2**: Depends on Phase 2 and reuses Bookmark persistence/UI created in US1. Its tests and tag/search modules can begin after Phase 2, but integration tasks T045–T049 require T034, T036, and T037.
- **Phase 5 — US3**: Depends on Phase 2 and reuses Bookmark persistence/UI created in US1. Its tests/services can begin after Phase 2, but T053–T058 require T034, T036, and T037; tag-edit integration also requires T043–T045.
- **Phase 6 — Polish**: Depends on every user story selected for delivery; T066–T068 run last.

### User Story Completion Order

```text
Setup → Foundation → US1 (MVP)
                    ├──→ US2
                    └──→ US3
US1 + US2 + US3 → Polish → Runtime review
```

- **US1** owns the base Bookmark/IconAsset persistence, metadata boundary, create/get/icon routes, and active-library card/composer.
- **US2** layers tags, FTS search, favorites, filters, and pagination onto the independently working US1 bookmark library.
- **US3** layers editing and lifecycle operations onto the independently working US1 bookmark library; its core lifecycle does not require search, while tag-edit integration does.

### Within Each User Story

1. Write the story's tests and confirm they fail for the intended missing behavior.
2. Apply schema changes before repository code.
3. Implement pure validation/security modules before orchestration services.
4. Implement repositories before services, services before route handlers, and route handlers before UI integration.
5. Run the story-specific unit, integration, contract, and browser tests at the checkpoint.

## Implementation Strategy

### MVP First

1. Complete Setup and Foundation.
2. Complete US1 from failing tests through the story checkpoint.
3. Demonstrate address-only save, retrieved details, safe fallback, editable title, duplicate choice, and reopen-link behavior.
4. Stop and validate before adding organization or maintenance features.

### Incremental Delivery

1. **MVP**: US1 provides a private, usable bookmark list with the approved saving experience.
2. **Organization increment**: US2 adds tags, favorites, search, filtering, and scale validation.
3. **Maintenance increment**: US3 adds editing, archive/restore, optimistic conflicts, and confirmed deletion.
4. **Release hardening**: Phase 6 proves cross-story requirements and prepares the review runtime.
