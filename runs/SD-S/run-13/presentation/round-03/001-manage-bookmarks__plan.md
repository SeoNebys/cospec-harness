# Implementation Plan: Bookmark Manager

**Branch**: `001-manage-bookmarks` | **Date**: 2026-09-23 | **Spec**: [spec.md](spec.md)

**Input**: Approved feature specification from `specs/001-manage-bookmarks/spec.md`

## Summary

Build a responsive, single-user bookmark manager as one deployable TypeScript web application. A React browser client provides fast create, edit, search, filter, favorite, sort, and delete flows. A Fastify server owns validation, SQLite persistence, and guarded retrieval of page titles and descriptions. The production server serves both the API and the compiled client on `0.0.0.0:4000`; data persists in a local SQLite file.

Page-detail retrieval is a server-side operation so it works independently of browser cross-origin rules. It accepts only public HTTP(S) destinations, validates every DNS result and redirect hop, pins the outbound connection to an approved public address, enforces an 8-second total deadline and 1 MiB response limit, and parses only HTML metadata as plain text. Retrieval failures return an editable domain-based title and blank description rather than blocking bookmark creation.

## Technical Context

**Language/Version**: Node.js 24.x with TypeScript 5.x; modern browser JavaScript generated by the client build

**Primary Dependencies**: React 19, Vite 7, Fastify 5, `@fastify/static`, Zod 4, Cheerio 1, Undici 7, and `ipaddr.js`; versions are locked in `package-lock.json`

**Storage**: File-backed SQLite through Node 24's built-in `node:sqlite`; schema migrations are checked-in SQL files, foreign keys and defensive mode are enabled, and extension loading remains disabled

**Testing**: Vitest for shared/client unit tests, Vitest plus Fastify injection for server integration and contract tests, and `@playwright/test` 1.61.0 with the preinstalled Chromium for end-to-end desktop and mobile-view validation

**Target Platform**: Linux-hosted web application, served on `0.0.0.0:4000`; current evergreen desktop and mobile browsers

**Project Type**: Single-package web application with client, HTTP server, shared contracts, and local persistent data

**Performance Goals**: Search/filter/sort updates visible within 1 second for 95% of interactions with 10,000 bookmarks; normal metadata retrieval visible within 5 seconds; failed retrieval resolves to a savable fallback within 10 seconds

**Constraints**: One process and one local database; no accounts or in-app authorization; intended for a private/self-hosted deployment boundary; public HTTP(S) metadata targets only; 8-second fetch deadline, 1 MiB body cap, at most 5 validated redirects; responsive and keyboard-accessible UI; user-entered values preserved after validation errors

**Scale/Scope**: One user, up to 10,000 bookmarks, up to 20 tags per bookmark, one primary library screen plus create/edit and delete-confirmation dialogs; sharing, import/export, extensions, generated summaries, and link monitoring remain out of scope

## Architectural Decisions

### Runtime shape

- Development uses separate Vite and Fastify processes for rapid client iteration, with `/api` proxied to the server.
- Production builds client and server artifacts, then starts a single Fastify process. Fastify serves the compiled client, API routes, and a client-side navigation fallback.
- The application binds to `0.0.0.0`; port `4000` is the default and can be overridden for tests only.
- `data/bookmarks.sqlite` is the default persistent database. Tests use isolated temporary databases.

### Request and data flow

1. The client normalizes basic form input and calls `POST /api/page-metadata` after a valid address settles for 400 ms or the user explicitly retries.
2. The server normalizes the URL, rejects credentials and non-HTTP(S) schemes, resolves all destination addresses, rejects non-public ranges, and performs a bounded request with redirects disabled.
3. Each redirect is resolved and validated as a new destination before the next request. The outbound connection uses the validated address while retaining the original hostname for HTTP host and TLS verification.
4. The server accepts HTML/XHTML only, reads at most 1 MiB, extracts a normalized title and description, and returns retrieval status plus the final URL. On failure it returns a non-fatal fallback response.
5. The client never overwrites a title or description once the user has edited that field. Changing the URL marks existing metadata stale and requires an explicit refresh/replacement choice.
6. Bookmark mutations are validated again on the server and committed transactionally with tag relationships.
7. Library queries apply search, filters, and sorting in SQLite and return the current result set plus aggregate tag options.

### Quality and operations

- Shared Zod schemas define request/response shapes used by both client and server; OpenAPI documents the externally observable contract.
- Errors use stable machine-readable codes plus user-safe messages; server logs retain operational context without logging page bodies or personal notes.
- Database migrations run at startup before the port begins accepting traffic and are recorded in a schema-migrations table.
- The root UI receives `data-harness-ready="true"` only after the initial library request succeeds or returns a valid empty state.
- Graceful shutdown stops accepting requests and closes the database.
