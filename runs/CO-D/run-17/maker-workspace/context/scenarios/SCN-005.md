Scenario ID: SCN-005
Title: Edit a saved link's address with reviewed re-fetch and guards
Type: Happy Path
Approval status: approved
Approval session: SESSION-001
Approval cycle: 1

## Approved behaviour
While editing a saved card the client can also change the web address. Changing
the address is treated as significant: the client presses "Fetch page details"
to look up the new page and review it before committing. The newly fetched
preview, icon, and source update, but the client's deliberately written title and
description are preserved. The app quietly offers the newly fetched title and
description as separate "Use this" choices, so the client can adopt either piece
independently or keep their own. Saving commits the new address and details. An
unusable new address is refused with a message, and changing the address to one
already used by another saved link is blocked.

## Gherkin
Feature: Editing a saved link's address

  Scenario: Change the address and review the new page before committing
    Given the client is editing a saved card with a hand-written title
    When the client changes the address to another valid page and presses "Fetch page details"
    Then the preview, icon, and source update to the new page
    And the hand-written title and description are preserved
    And the new page's title and description are offered as separate "Use this" choices
    When the client presses "Save changes"
    Then the card points to the new address with the kept or adopted details

  Scenario: Adopt only one suggested field
    Given fetched suggestions are shown for a changed address
    When the client presses "Use this" for the description only
    Then the description becomes the suggested one and the title keeps the client's wording

  Scenario: Refuse an unusable new address
    Given the client is editing a saved card
    When the client changes the address to "not a real address" and tries to fetch or save
    Then the change is refused with a message and nothing is committed

  Scenario: Block changing to an address another link already uses
    Given two saved links exist
    When the client edits one and changes its address to the other's address
    Then the change is blocked with a message

  Scenario: Require review after an address change before saving
    Given the client changed the address but has not fetched the new page
    When the client presses "Save changes"
    Then saving is blocked with a prompt to fetch the new page's details first

## Assumptions
- An address change requires an explicit "Fetch page details" step before it can
  be committed (no silent detail swap while typing).
- Suggested title and description are offers, never forced replacements.
