Scenario ID: SCN-004
Title: Find bookmarks with a precise search query language
Type: Happy Path
Approval status: approved
Approval session: SESSION-001
Approval cycle: 1

## Approved behaviour
The client searches the collection from a single search box. Search is
case-insensitive and, by default, looks across the title, description, note,
tags, and the site address, matching where the words occur and highlighting the
matched text on each result card. The result count reflects how many of the
whole collection matched.

The client can also use a precise query language:
- A plain word matches wherever it occurs (title/description/note/tags/address).
- `#tag` matches that tag specifically and exactly (e.g. `#css` does not match a
  tag `css-frameworks`).
- Several terms together require all of them (implicit AND), e.g. `flexbox #css`.
- Text in double quotes matches that exact phrase.
- Terms can be combined with `AND`, `OR`, `NOT`, and parentheses, e.g.
  `rome (#article OR #book)`.
- Putting an operator word in quotes treats it as ordinary text rather than an
  operator (e.g. `"OR"` searches for the letters "or").

When the query is malformed (for example an unmatched parenthesis), the app shows
a clear warning message and shows no results, so it is obvious the search must be
corrected rather than appearing to match everything. Fixing the query restores
results immediately. A short, unobtrusive syntax reminder is shown near the
search box.

## Gherkin
Feature: Search the collection

  Scenario: Default search across all fields, case-insensitive, highlighted
    Given the collection contains bookmarks
    When the client types one or more plain words into the search box
    Then only bookmarks containing all those words (ignoring case) in the title,
         description, note, tags, or address are shown
    And the matched text is highlighted on each result
    And the count shows how many of the whole collection matched

  Scenario: Tag-specific term matches tags exactly
    When the client searches "#reference"
    Then only bookmarks that carry "reference" as a tag are shown
    And a bookmark whose tag merely starts with or contains "reference" is not
        matched by the tag term

  Scenario: Words and tags combine with implicit AND
    When the client searches "flexbox #css"
    Then only bookmarks that contain the word flexbox and carry the tag css are shown

  Scenario: Quoted text matches an exact phrase
    When the client searches for a quoted phrase
    Then only bookmarks containing that exact phrase are shown

  Scenario: Boolean operators and parentheses
    When the client searches "rome (#article OR #book)"
    Then bookmarks matching rome and (tagged article or tagged book) are shown
    And searching "rome NOT #book" excludes bookmarks tagged book

  Scenario: Quoting an operator makes it ordinary text
    When the client searches "\"OR\""
    Then the query searches for the literal text "or" instead of applying the OR operator

  Scenario: Malformed query shows a clear warning and no results
    When the client enters a query with an unmatched parenthesis
    Then a clear warning message is shown (e.g. about an unmatched parenthesis)
    And no results are shown
    When the client corrects the query
    Then the matching results are shown again

## Assumptions
- Tag matching is exact (case-insensitive equality), by explicit client choice.
- Operator precedence is NOT before AND before OR; parentheses override.
- A quote left unclosed is tolerated (treated as running to the end of the text);
  only parenthesis balance is validated as a hard error in this cycle.
