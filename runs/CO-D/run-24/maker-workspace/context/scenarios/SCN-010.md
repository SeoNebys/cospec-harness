Title: Saving edge cases — invalid address, fetch failure, archived duplicate
Type: Error Case
Approval status: approved
Approval session: SESSION-001
Approval cycle: 1

## Approved behaviour

Invalid address (error/exception perspective):
- A clearly invalid entry (e.g. free text with spaces, no domain) is rejected on
  Save with a gentle inline message; nothing is saved.
- A bare domain like "example.com" is accepted; the app adds "https://" for the
  client.

Page-detail fetch failure (error/exception perspective):
- If page details cannot be fetched, the bookmark is still saved (the link is
  never lost). The card shows a small warning that details couldn't be fetched and
  invites the client to add a title/description via Edit, which works normally.

Archived duplicate (functional-path perspective, ties to SCN-001/005):
- Pasting a link that already exists but is archived does not create a duplicate.
  The app switches to the "Archived" tab, makes the archived state clear, and opens
  the existing bookmark's editor, so the client can choose to edit it, restore it,
  or leave it archived.

## Gherkin

Feature: Saving edge cases

  Scenario: Reject clearly invalid address
    When the client tries to save free text that is not a web address
    Then it is not saved and a gentle inline message is shown

  Scenario: Accept a bare domain
    When the client saves "example.com"
    Then it is accepted and treated as "https://example.com"

  Scenario: Save despite fetch failure
    Given page details cannot be fetched for a valid address
    When the client saves it
    Then the bookmark is still saved
    And a warning invites the client to add title/description via Edit

  Scenario: Re-saving an archived link
    Given a link is already saved and archived
    When the client pastes and saves it again
    Then no duplicate is created
    And the client is taken to the archived original with its archived state made clear
    And its editor opens so they can edit, restore, or leave it archived

## Assumptions

- Address validity requires a plausible domain (a dot, no spaces) or localhost.
- Fetch failure never discards the link; details are user-fillable afterwards.
- Archived-duplicate routing reveals the archived state and offers Restore.
